**The nightly memory run no longer crashes when an older recall rebuilds the chat index under it.** An agent's MCP server keeps the release it started with until the agent restarts, so after an upgrade it rebuilt the chat tables back to its own schema, and a run reading them stopped with `no such column: s.root`. Now a recall process that an upgrade has outlived leaves the index alone and asks for the agent to be restarted, and a nightly run that finds the chat tables changed under it leaves the chats for the next run and records why. After upgrading, restart agents that were already open.
